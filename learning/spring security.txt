  Core Concepts: Why Spring Security and JWT?

   * Why Security is Needed: In any application with user accounts and protected resources, you need a robust security
      layer. This layer is responsible for:
       * Authentication: Verifying a user's identity (are you who you say you are?). This is typically done with a
         username/password, biometrics, or other credentials.
       * Authorization: Determining if an authenticated user has permission to access a specific resource or perform
         an action (are you allowed to do this?). This is often managed through roles and permissions.

   * Why Spring Security? Spring Security is the standard for securing Spring-based applications. It's a powerful and
     highly customizable framework that handles most of the heavy lifting for authentication and authorization.
     Instead of writing this complex and critical logic from scratch (which is prone to errors and vulnerabilities),
     you can leverage Spring Security's battle-tested components.

   * Why JWT (JSON Web Token)? JWT is a modern and popular way to handle authentication in web applications,
     especially in the context of REST APIs and single-page applications (SPAs). Here's why it's a good choice:
       * Stateless: The server doesn't need to store any information about the user's session. The JWT itself contains
          all the necessary information (user ID, roles, expiration time). This makes the application more scalable,
         as any instance of the application can validate the token.
       * Decoupled: Your frontend and backend are decoupled. The frontend receives the JWT and sends it with every
         request to a protected endpoint. The backend simply validates the token.
       * Portable: JWTs are a standard (RFC 7519) and can be used across different technologies and platforms.

  The Security Flow in Your Application

  Here's a step-by-step breakdown of how a user interacts with your application's security:

  1. User Registration:

   * A new user (either a Faculty or a Student) sends a POST request to /api/auth/register/faculty or
     /api/auth/register/student with their details (name, email, password, etc.).
   * The AuthController receives this request.
   * The AuthService handles the registration logic.
   * Crucially, before saving the user to the database, the AuthService uses a PasswordEncoder (specifically,
     BCryptPasswordEncoder) to hash and salt the user's password. This is a critical security practice. You should
     never store passwords in plain text.

  2. User Login:

   * The user sends a POST request to /api/auth/login with their email and password.
   * The AuthController passes the request to the AuthService.
   * The AuthService uses Spring Security's AuthenticationManager to authenticate the user.
   * The AuthenticationManager relies on the UserDetailsServiceImpl. This service is responsible for loading the
     user's data from the database (from either the FacultyRepo or StudentRepo) based on the provided email.
   * The UserDetailsServiceImpl returns a UserDetails object, which is a Spring Security representation of the user,
     including their username, password (the hashed one from the database), and roles (e.g., ROLE_TEACHER,
     ROLE_STUDENT).
   * The AuthenticationManager compares the password provided by the user (after hashing it) with the hashed password
     from the database.
   * If the authentication is successful, the AuthService calls the JwtTokenProvider to generate a JWT.

  3. JWT Generation and Response:

   * The JwtTokenProvider creates a JWT. This token is a long string with three parts separated by dots:
       * Header: Contains the algorithm used to sign the token (e.g., HS512).
       * Payload: Contains the "claims" about the user, such as their email (the "subject"), their roles, the token's
         issuance time, and its expiration time.
       * Signature: A cryptographic signature that verifies the token's authenticity. It's created using the header,
         payload, and a secret key that is only known to the server. This prevents the token from being tampered with.
   * The AuthController sends a LoginResponse back to the user, which includes the JWT.

  4. Accessing Protected Resources:

   * Now, when the user wants to access a protected endpoint (e.g., /api/faculty/all), they must include the JWT in
     the Authorization header of their HTTP request, like this: Authorization: Bearer <the_jwt_token>.
   * This is where the JwtAuthenticationFilter comes into play. This filter intercepts every incoming request.
   * The JwtAuthenticationFilter checks for the Authorization header. If it finds a JWT, it validates it using the
     JwtTokenProvider.
   * The JwtTokenProvider checks the token's signature (using the secret key) and its expiration date.
   * If the token is valid, the JwtTokenProvider extracts the user's email and roles from the token's payload.
   * The JwtAuthenticationFilter then creates an Authentication object and sets it in Spring Security's
     SecurityContextHolder. This tells Spring Security that the current user is authenticated.
   * Finally, the request is allowed to proceed to the controller.

  5. Authorization at the Controller Level:

   * The SecurityConfig file defines which roles are required for which endpoints. For example:

   1     .requestMatchers("/api/faculty/**").hasRole("TEACHER")
   2     .requestMatchers("/api/student/**").hasRole("STUDENT")
   * When the request reaches the controller, Spring Security checks if the authenticated user (from the
     SecurityContextHolder) has the required role.
   * If the user has the correct role, the controller method is executed.
   * If the user does not have the correct role, a 403 Forbidden error is returned.

  6. Handling Unauthorized Access:

   * If a user tries to access a protected endpoint without a valid JWT, the JwtAuthenticationEntryPoint is triggered.
      It returns a 401 Unauthorized error, telling the client that they need to authenticate first.

  Summary of the Code's Purpose

   * `SecurityConfig.java`: The central configuration for your security setup. It wires everything together, defines
     the security rules, and tells Spring Security to use your custom JWT filter.
   * `JwtTokenProvider.java`: The "brains" of your JWT operations. It creates, validates, and parses JWTs.
   * `JwtAuthenticationFilter.java`: The "gatekeeper" that inspects every request for a JWT and sets up the security
     context if the token is valid.
   * `JwtAuthenticationEntryPoint.java`: The component that handles authentication failures.
   * `UserDetailsServiceImpl.java`: The bridge between your application's user models (Faculty, Student) and Spring
     Security's UserDetails interface.
   * `AuthService.java`: The service that orchestrates the login and registration processes.
   * `AuthController.java`: The entry point for authentication-related API calls.

  This entire setup provides a secure, stateless, and scalable authentication and authorization system for your
  AutoGrade application, which is essential for protecting user data and ensuring that only authorized users can
  perform specific actions.

           * `sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))`: This is a

         User object with the faculty's email, hashed password, and role.
       * If no faculty member is found, it searches the StudentRepo.
       * If no user is found in either repository, it throws a UsernameNotFoundException.

   3. `JwtAuthenticationFilter.java`: This filter is the gatekeeper for your protected endpoints. It runs on every

       * `doFilterInternal(...)`: This method contains the core logic of the filter.

  The Complete Authentication and Authorization Flow

   1. Login Request: A user submits their email and password to /api/auth/login.
   2. Authentication: Spring Security's AuthenticationManager uses your UserDetailsServiceImpl to fetch the user's data
       and PasswordEncoder to verify the password.
   3. Token Generation: If authentication is successful, the JwtTokenProvider generates a JWT.
   4. Token Response: The JWT is sent back to the client.
   5. Subsequent Requests: The client stores the JWT (e.g., in local storage) and sends it in the Authorization header
      for all future requests to protected endpoints.
   6. Token Validation: Your JwtAuthenticationFilter intercepts each request, validates the JWT using the
      JwtTokenProvider, and sets the user's authentication context.
   7. Authorization: Spring Security's authorization mechanism checks if the authenticated user has the required role
      to access the requested endpoint (as defined in SecurityConfig).
   8. Access Granted/Denied: If the user is authorized, the request proceeds to the controller. If not, a 403 Forbidden
       error is returned. If the token is invalid or missing, a 401 Unauthorized error is returned.

  The "Why": A Secure and Modern Approach

  This project uses Spring Security with JSON Web Tokens (JWT) to protect your API. This is a standard and robust
  approach for modern web applications for a few key reasons:

   * Separation of Concerns: Your frontend (the user interface) and backend (your Spring Boot API) can be completely
     separate. The frontend only needs to get a JWT and send it with its requests.
   * Statelessness: The server doesn't need to keep track of user sessions. The JWT itself contains all the
     information needed to verify a user's identity and permissions. This makes your application more scalable and
     easier to maintain.
   * Explicit Security: The security rules are clearly defined in one place (SecurityConfig.java), making it easy to
     see which parts of your application are public and which are protected.

  The Complete Security Flow: Step-by-Step

  Here is the journey of a user from registration to accessing a protected part of your application:

  Step 1: Registration (Creating a New User)

   1. The Request: A new user wants to register. They send a POST request to either /api/auth/register/faculty or
      /api/auth/register/student. This request's body contains their details, including a plain-text password.
   2. The Controller (`AuthController.java`): The registerFaculty or registerStudent method in your AuthController
      receives this request.
   3. The Service (`AuthService.java`): The controller calls the AuthService. This service handles the business logic
      for creating a new user.
       * Password Encryption: Before saving the new user to the database, the AuthService uses a PasswordEncoder
         (specifically, BCryptPasswordEncoder) to hash the user's password. This is a critical security step. It
         ensures that you are not storing plain-text passwords, so even if your database is compromised, the passwords
         are not immediately exposed.
       * Saving the User: The service saves the new Faculty or Student object to the database with the hashed password.
   4. Automatic Login: After a successful registration, the AuthService immediately authenticates the new user and
      generates a JWT for them. This provides a smooth user experience, as the user doesn't have to log in right after
      registering.
   5. The Response: The AuthController sends a response back to the user with the newly generated JWT.

  Step 2: Login (Authenticating an Existing User)


   1. The Request: An existing user wants to log in. They send a POST request to /api/auth/login with their email and
      plain-text password.
   2. The Controller (`AuthController.java`): The login method in your AuthController receives this request.
   3. The Service (`AuthService.java`): The AuthService is called. It uses Spring Security's AuthenticationManager to
      handle the authentication process.
   4. The `UserDetailsServiceImpl.java`: The AuthenticationManager needs to know where to find the user's information.
      It calls your UserDetailsServiceImpl.
       * This service looks for a user (either a Faculty or a Student) in the database by their email address.
       * If a user is found, it returns a UserDetails object, which contains the user's email, their hashed password
         from the database, and their role (e.g., ROLE_TEACHER).
   5. Password Verification: The AuthenticationManager now has the password the user typed in and the hashed password
      from the database. It uses the PasswordEncoder to hash the password the user provided and compares it to the one
      from the database.
   6. Token Generation (`JwtTokenProvider.java`): If the passwords match, the user is successfully authenticated. The
      AuthService then calls the JwtTokenProvider to create a JWT.
       * The generateToken method in JwtTokenProvider creates a token that includes the user's email (as the
         "subject"), their roles (as a "claim"), and an expiration date.
       * This token is then signed with a secret key (from your application.properties or .env file). This signature is
         what guarantees that the token is authentic and has not been tampered with.
   7. The Response: The AuthController sends a LoginResponse to the user, which contains the JWT. The user's browser
      will then typically store this token (e.g., in local storage).

  Step 3: Accessing a Protected Resource

   1. The Request: The user now wants to access a protected endpoint, for example, /api/faculty/all. To do this, they
      must include the JWT in their request's Authorization header, like this:
      Authorization: Bearer <the-jwt-that-was-returned-on-login>
   2. The Filter (`JwtAuthenticationFilter.java`): This filter intercepts every request to your application.
       * It checks if the Authorization header is present and starts with "Bearer ".
       * If it is, it extracts the JWT.
   3. Token Validation (`JwtTokenProvider.java`): The filter calls the validateToken method in your JwtTokenProvider.
       * This method checks the token's signature to make sure it's authentic.
       * It also checks if the token has expired.
   4. Setting the Security Context: If the token is valid, the filter gets the user's email from the token and uses
      your UserDetailsServiceImpl to load the user's details. It then creates an Authentication object and places it in
       the SecurityContextHolder. This is how the rest of the application knows who the current user is for this
      request.
   5. Authorization (`SecurityConfig.java`): The request is now allowed to proceed. Spring Security checks the rules
      you defined in SecurityConfig.
       * The rule for /api/faculty/** is hasRole("TEACHER").
       * Spring Security looks at the Authentication object in the SecurityContextHolder and checks if the user has the
         ROLE_TEACHER authority.
   6. The Final Result:
       * If the user has the `ROLE_TEACHER` role: Access is granted, and the request is passed to the
         FacultyController.
       * If the user does *not* have the `ROLE_TEACHER` role: Access is denied, and a 403 Forbidden error is sent back.
       * If the JWT was invalid, expired, or missing: The JwtAuthenticationFilter would have failed to authenticate the
         user, and the JwtAuthenticationEntryPoint would have sent a 401 Unauthorized error.


  This entire process provides a secure, stateless, and well-structured way to manage authentication and
  authorization in your application, ensuring that your data and endpoints are properly protected.
